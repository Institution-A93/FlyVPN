# ADR-0019: Telegram-бот — Python/aiogram (исключение из Go-инварианта)

- Статус: accepted
- Дата: 2026-06-24

## Контекст
ADR-0013 и инвариант в `CLAUDE.md` фиксируют: backend-сервисы control plane пишутся
на Go. Появляется новый компонент — **Telegram-бот** (онбординг, выдача профиля,
доставка уведомлений об окончании трафика/подписки). Это не часть control-plane
data/auth-плоскости, а отдельный публичный канал со своим жизненным циклом.

Бот уже реализован на **Python/aiogram** (быстрый прототип, см. `services/bot`).
aiogram — зрелый OSS-фреймворк (соответствует инварианту «только OSS») с богатой
экосистемой именно под Telegram. Переписывать на Go ради буквы инварианта —
неоправданные затраты без выгоды для продукта.

## Решение
Бот живёт в монорепо как `services/bot` на **Python 3 / aiogram**, что является
**осознанным точечным исключением** из «backend — Go» (ADR-0013). Исключение
ограничено ботом; config-api, orchestrator и любые сервисы data/auth-плоскости
остаются на Go.

Условия исключения:
- Бот **автономен** и общается с control plane только через стабильные API
  (позже — `config-api`), не лезет напрямую в БД/RADIUS.
- Тот же режим секретов и деплоя, что у Go-сервисов: креды из vault (ADR-0012),
  systemd + Ansible-роль `bot`, лицензия AGPL-3.0.
- Только OSS-зависимости (aiogram, aiohttp, python-dotenv).

## Хостинг
На control plane (Hetzner), не на egress — камуфляж egress (ADR-0011), производительность
data-plane и blast-radius. Режим — long-polling (входящих публичных портов нет;
`/notify` только на localhost). Webhook-режим (если понадобится) — отдельный VPS,
оформляется отдельным ADR.

## Следствия
- В монорепо появляется Python-тулчейн (только для `services/bot`): venv + pip в
  Ansible-роли `bot`. CI для бота — отдельный шаг (lint/импорт-смоук), не Go-pipeline.
- Инвариант «backend — Go» в `CLAUDE.md` читается с оговоркой: исключение для
  `services/bot` по этому ADR.
- Если Python-сервисов станет больше одного — пересмотреть инвариант отдельным ADR
  (этот разрешает ровно бот).
